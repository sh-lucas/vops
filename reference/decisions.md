# Decisions

Every non-obvious choice made while building vops, with the reason. Newest last. If you change one, update it here.

## Shape

- **One binary, `vops`.** Same binary is the local CLI, the remote CLI, the daemon (`vops daemon`) and the proxy (`vops proxy`). Install = copy the binary over ssh. No scp, no rsync: `ssh host 'cat > file' < binary`.
- **Go deps: 4.** `modernc.org/sqlite` (pure Go, keeps the binary static so it can be copied anywhere), `go.yaml.in/yaml/v3` (compose files; writing a YAML parser is not worth it), `golang.org/x/crypto` (autocert for Let's Encrypt, ssh key parsing), `filippo.io/age` (the secrets backup, pure Go). Everything else is stdlib.
- **Runtime deps on the host:** linux, systemd, podman (netavark backend), git. btrfs (+ btrfs-progs) enables snapshots and rollback; without it everything else works and the dashboard says why snapshots are off.
- **Our own reverse proxy, in its own process.** No Caddy/Traefik/nginx: rolling releases need to flip traffic the moment a new replica is ready, and our proxy does it with a map swap instead of a config reload. TLS comes from autocert (HTTP-01 + TLS-ALPN-01). It runs as `vops proxy` (`vops-proxy.service`), not inside the daemon: a panic, OOM or deadlock in the daemon, or an upgrade (which restarts it), used to take every site down. See "The proxy process".
- **The CLI talks to the host through ssh only; the dashboard and the registry are the web-facing parts.** `vops status` locally runs `ssh host ~/.vops/bin/vops status` there; the remote vops talks to the daemon over a unix socket (`~/.vops/vops.sock`). ssh is the auth for the CLI. The only network-facing surfaces are the dashboard + its api (`vops.<domain>`, an admin's password + session cookie), the registry (`registry.<domain>`, basic auth: admins' passwords, deployers' tokens) and the apps' own routes. Deploys (`sync`, `apply`, `install`) never go through the web; the dashboard can do apply, rollback, env, users and previews once logged in.

## Git sync

- `~/vops` is a normal (non-bare) repo with `receive.denyCurrentBranch=updateInstead`. A `git push` updates the working tree directly, no hooks, no checkout step. It refuses if someone edited tracked files on the server, which is what we want.
- `vops sync` = `git pull vops main` → `git push vops HEAD:main` → remote `vops plan` → show → confirm → remote `vops apply --commit <sha>`. Apply refuses if the remote HEAD moved since the plan.
- Plain `git push vops` also works; nothing is deployed until `vops sync`, `vops apply` or the "apply" button in the UI (which shows the pending plan first).
- `vops-lock.yml` (gitignored) holds `host`, `port`, `ssh_key`. Flags `--host`/`--ssh-key` override it, so CI needs no file.

## Projects & compose

- A project is any git-tracked directory containing `compose.yml`, `compose.yaml`, `*.compose.yml` or `docker-compose.yml`. Several compose files in one dir are merged (duplicate service = error). Nested dirs are separate projects.
- vops parses compose itself and calls `podman run`. No podman-compose/docker-compose: they can't do rolling releases and are one more dependency. Unsupported keys are an **error**, not silently ignored.
- Project `a/b` gets domain `b.a.<domain>`. A routed service gets `<service>.b.a.<domain>`; if it is the only routed service of the project it also gets `b.a.<domain>`. Extra domains via `x-vops.domains`.
- Routing is opt-in per service with `x-vops.port` (the HTTP port inside the container).
- Default `restart: unless-stopped` (compose default is `no`, which is a bad default for a server).
- Interpolation (`${VAR}`, `${VAR:-x}`, `${VAR:?err}`, `$$`) uses the project env vars stored by vops, not the shell. `environment: [KEY]` passes the project var through.

## Networking

- Each project has network `vops-<project>`; services resolve each other by service name (compose behaviour).
- Every container also joins the shared network `vops` with alias `<service>.<project reversed>` (e.g. `db.sub.proj`), so any project can reach any other one by a predictable name.
- The proxy reaches containers through a port published on `127.0.0.1:<port>`; vops picks the port (stable across restarts). Works the same rootless or rootful.
- netavark is required (aliases + DNS). CNI setups without dnsname don't resolve names.
- Compose `networks` work like compose: no `networks` = project `default` + shared `vops`; with `networks` = exactly those. `vops` is a reserved key for the shared network, so a service can opt in explicitly and a db on an internal network stays invisible to other projects.
- Networks carry a `vops.nethash` label with the hash of their definition. A changed definition means remove the project's containers on it, recreate, redeploy (podman can't change a network in place). The default network created before networks were configurable has no hash; it is accepted as long as it is still a plain bridge, so upgrading doesn't restart everything.
- Service hashes include the hash of the networks they join, so a network change redeploys its services.

## Deploys

- Desired state = git + env vars. Actual state = podman containers with `vops.*` labels. The db is not the source of truth for containers; the daemon rebuilds its routing table from podman on start.
- Each service has a hash of everything that defines it (resolved args, image, own-registry digest, build context tree hash). Different hash = redeploy. The hash of an unchanged service must stay the same across vops versions, or an upgrade redeploys everything (`TestServiceHashIsStable` guards it); migrations are additive for the same reason.
- Strategy: `rolling` for routed services (new replicas → readiness → switch traffic → drain 2s → stop old), `recreate` for everything else (two postgres on the same volume is how you lose data). Override with `x-vops.strategy`.
- Readiness: compose `healthcheck` (vops runs `podman healthcheck run` itself, so it works without systemd timers) → else `x-vops.health` HTTP path → else TCP connect on the routed port → else "still running after 2s". Failed readiness removes the new replicas and keeps the old ones.
- `build:` builds on the host, tagged with the git tree hash of the context, so it only rebuilds when the context changes.

## Registry (own implementation)

- OCI distribution spec, stdlib only, filesystem storage: `blobs/sha256/<ab>/<digest>`, `repos/<name>/tags/<tag>` (file with the digest), `repos/<name>/manifests/<digest>` (empty marker file), `uploads/<uuid>`.
- Auth is HTTP Basic over HTTPS. Two roles, in the `users` table. Admins log into the dashboard and push/pull every repo with their password (pbkdf2, 600k). Deployers never log into the dashboard; they get a random token (stored as sha256: high-entropy tokens don't need slow hashing) and push/pull every repo (`global`) or the repos in `user_repos`. Push and pull are one permission: a CI that pushes also pulls its base, and a pull-only token proved to be a distinction nobody used.
- This replaced "the dashboard admin pulls everything and pushes nothing" and the per-user regex: an admin could create a user that pushes anything anyway, so refusing its own pushes only added a second credential; a regex was a footgun (`shop.*` matches `shopping/x`) and exact names cover every real case. The migration turns `.*`/`.+` into global, json repo lists into rows, drops any other regex with an `auth` event naming the user, and makes the old dashboard password the `admin` user.
- Repo names are normalized in Go (trimmed, everything after the first `:` dropped, so `shop/web:latest` is `shop/web`, deduped) and the db refuses a `:` or an empty name anyway.
- The rules live in the db, so no code path can break them: `CHECK`s (role is admin or deployer; admins are global; admins' secrets are pbkdf2 `salt:key`, deployers' aren't), `RAISE(ABORT)` triggers (the last admin can't be deleted or demoted; a global user can't get repos) and cascades (setting global deletes the user's repos; deleting a user deletes its repos and sessions; a demotion or a new secret deletes its sessions). `PRAGMA foreign_keys` is on for every connection (the dsn), so the cascades are real.
- `vops-internal` is reserved (a `CHECK`), the name of the daemon's own loopback pull user.
- The daemon pulls its own images through the loopback UI listener with an in-memory token, then tags them with the public name. No DNS/TLS needed for the server to deploy its own images.
- Watchtower replacement: pushing a tag that a service uses redeploys that service (rolling). Opt out with `x-vops.watch: false`.
- GC is mark & sweep: untagged manifests (not referenced by a tagged index or as the subject of a kept one) and unreferenced blobs go; anything younger than 1h is kept so pushes in progress are safe. Runs daily, from `vops registry gc` and from the dashboard. Uploads older than 24h are dropped.
- GC also keeps a set of digests it is given: what pins run, previews' overrides by digest, and every image of the newest `image_keep` (10) deploy rows per project. Pushing `latest` again leaves the old digest untagged; without this, image rollback and "Preview from here" would break at the next gc. A count of deploys (not days) because rollback is "the last few versions", whatever the release pace. Older rows keep showing; their image is marked gone (the registry no longer has it) and rollback skips it with that reason.

## Logs

- Containers use podman's `journald` log driver with tag `vops.<project>.<service>`. journald already does aggregation, rotation, compression, indexing and history across replicas. Reading = `journalctl`, falling back to `podman logs`.
- Search is `journalctl --grep` (PCRE2 builds; the text is regex-escaped, case-insensitive): it reads backwards until n matches, so it covers the whole history without loading it. Without PCRE2, go filters the last 20k lines.
- Paging: every response carries `X-Vops-Before`, the journald cursor of its oldest line; `?before=<cursor>` returns the n lines before it (`journalctl -r --after-cursor`). The dashboard loads them when scrolled to the top. No header = start of logs. Following = read history to the end, then `-f --after-cursor=<newest>` (no gap, no "silence means caught up" guess).
- The dashboard keeps at most 5000 lines while following; older ones are dropped (Reload to browse history again), so a tab left open doesn't grow forever.
- The dashboard filters by time with `since`/`until` (unix seconds; a set "to" means a closed range, so no follow), shows the available range from `X-Vops-First`/`X-Vops-Last` next to the range loaded, and downloads what is in view as `<project>[-<service>]-YYYYMMDD-HHMM.txt` or `.csv` (time, service, message; split in the browser). From/to are a date input plus an optional time input (empty = 00:00 / 23:59), because `datetime-local` yields no value until every field is filled.
- Date filter: `?since`/`?until` (unix seconds) map straight to `journalctl --since=@n`/`--until=@n`; `until` closes the range so follow is skipped. `X-Vops-First`/`X-Vops-Last` (unix seconds, set only on the first page) give the whole journal's range for these services regardless of grep/since/until, so the UI can show "logs available from X to Y".
- Lines carry the host's local time as text (the cli runs on the host); `X-Vops-Offset` (host UTC offset, seconds) lets the dashboard rewrite them to the browser's zone, the same zone as its from/to inputs.
- DuckDB/parquet was proposed; rejected for now: it needs cgo and a ~30MB library, which breaks "static binary, few resources". Revisit if searching logs across months becomes a real need.

## Web UI

- Plain HTML + CSS + vanilla JS, embedded with `embed`. It uses the same JSON API as the socket.
- Still no build step, no libraries, no external fonts or CDNs: it works offline. Everything is rendered with `h()` (never `innerHTML`).
- Layout: fixed sidebar (nav + project tree with a status dot: green running, amber pending/partial, red failing/invalid, grey disabled), a top bar with the host's commit, domain and a "pending changes" badge that opens plan/apply from any page. Below 880px the sidebar is a drawer. Light/dark follow the system.
- Status is polled every 10s by the shell (sidebar, top bar, the open alerts badge); pages subscribe instead of polling on their own.
- Project page = header + tabs (`#/p/<path>/<tab>`: services, timeline, previews, logs, env, events). A tab is one entry in `TABS` in app.js. Old links (`#/p/<path>`, `#/p/<path>/data` → timeline, `#/logs/<path>?service=x`, which is the full-page log view) keep working.
- System page (`#/system`, `/api/system`): read straight from `/proc` and `/sys` (no dependency, works rootless), no history. Rates and percentages are deltas against the previous sample, kept in the daemon: the first request samples twice 250ms apart, requests less than 1s apart share a result (the notifications' background sampling every 30s shares them too), so the page polls every 3s (15s in a background tab) at the cost of a few file reads. Disk io % busy is `io_ticks` of whole devices (`/sys/block`, minus loop/ram/zram); network counts physical links only (they have a `device`; bridges and veths would count the same bytes again), all but `lo` when none has one; link % only when `/sys/class/net/*/speed` knows it. Disk space is per filesystem holding `~/.vops` and the repo (merged when they share one). PSI rows hide when `/proc/pressure` is absent. Uptime (host and daemon) lives there too.
- Events: 50 per page, "Load more" pages back by id (`/api/events?n=&before=`), so new events don't shift pages. `vops events` asks for 100.
- Streamed actions started from a dialog (rollback, unpin, preview up) show their progress in a modal, like apply; closing it doesn't stop them.
- Destructive actions ask through an in-page `<dialog>` that states the consequences, not `confirm()`.
- Served on `ui` listen address (default `127.0.0.1:9984`) and on `vops.<domain>` over HTTPS. The default is loopback because plain HTTP with a password over the internet is bad; `vops ui` opens an ssh tunnel and the browser. Set `ui: ":9984"` in `vops.yml` to expose it.
- Sessions: random id in an `HttpOnly; SameSite=Strict` cookie, sha256 stored in sqlite with its user (the top bar shows it, events name it). Mutating requests also need the `X-Vops: 1` header (blocks CSRF without tokens). Only admins log in; a deployer's right token gets the same answer and event as a wrong password, so the login can't tell which names are deployers. Expired sessions are purged by the housekeeping tick.
- Env values are write-only: the API has no way to read them back.
- Json request bodies are capped at 1MB (`413` past it, `400` for malformed json); the backup upload is the one unbounded body, streamed and checked as it arrives. A test walks every route of the web api and expects `401` without a session and `403` without `X-Vops` on mutating ones, so a new route can't forget either.
- The env view (`/api/env/usage`, `vops env ls`) reports names and sources only, never values, not even of compose literals: it is computed by the same `compose.Load` + env merge the plan uses (the interpolator records which `${VAR}`s each environment entry uses), so it can't drift from what podman gets. A compose literal whose key matches `PASSWORD|SECRET|TOKEN|KEY|PRIVATE` (case-insensitive) is flagged: it is committed to git; the fix is `environment: [KEY]` + `vops env set`. A key nothing references (`environment: [KEY]` or `${KEY}` anywhere in the files; `COMPOSE_PROFILES` counts as used) is shown as unused.

## Install

- `vops install user@host` checks arch/podman/git/systemd and the host's vops version, uploads the binary and runs `vops setup` on the host, which: creates dirs, inits `~/vops`, writes the two systemd units, enables linger (non-root), restarts the daemon, (re)starts the proxy if needed and, when there is no admin, creates user `admin` and prints its password once. Running it again is the upgrade; there is no other command to learn.
- root → system units in `/etc/systemd/system/`; non-root → user units, need `net.ipv4.ip_unprivileged_port_start<=80` (setup tells you the sudo command if it isn't).
- `vops.service`: `KillMode=process` so restarting the daemon never kills containers. `vops-proxy.service`: no children, default kill mode, `RestartSec=1`.
- Setup always restarts the daemon (new code) but the proxy only when it isn't running, its unit file changed, or it reports another `proxy.Version` over `proxy.sock`, since restarting it is the only thing that interrupts the sites. The binary is replaced with `mv`, so a proxy that keeps running keeps its old inode: fine, its behaviour is what `proxy.Version` describes.
- Order: the daemon first, then the proxy. From v1.2 (one `vops.service` holding :80/:443) the restarted daemon no longer binds them, so the proxy starting next finds them free; if it doesn't (a slow stop), it exits and systemd retries every second, forever (`StartLimitIntervalSec=0`). Then setup asks the daemon to send its table (`POST /api/proxy/sync`), so the first start serves every route within a second or two. That migration costs a few seconds of downtime once, and setup says so.
- Both units are `Type=notify` (READY=1 once the sockets are bound, so `systemctl restart` returns when the process really serves; no more "wait 2s before trusting is-active") with a watchdog (`WatchdogSec=60` daemon, `30` proxy). The ping is sent only while a request to the process's own unix socket succeeds, so a deadlocked process is restarted (SIGABRT: Go prints every goroutine to the journal), not only a dead one. The daemon says READY before starting stopped containers after a reboot, so a slow podman can't hit the start timeout (its socket answers meanwhile; applies wait for the engine lock). sd_notify is ~50 lines of stdlib (`internal/sdnotify`), a no-op outside systemd.

## depends_on, jobs, profiles

- vops always waits for readiness between services, so `service_started` behaves like `service_healthy`. Stricter than compose, never looser.
- `service_completed_successfully` turns the dependency into a job: ready = exit 0, default `restart: no` (an always-restarting job would loop), 10 min timeout. A finished job isn't rerun until its definition changes (compose `up` does the same); a failed one is retried on the next apply.
- When a service fails, its dependents are skipped in that apply instead of deployed against a broken dependency.
- Active profiles come from `COMPOSE_PROFILES` in the project env: the compose-standard variable, set the vops way. `depends_on.restart` is rejected: vops never restarts dependents behind your back.

## Config: vops.yml and its lock

- One config file, `vops.yml`, committed: domain, email, listeners, tls, snapshots, images kept (`image_keep`), preview limits. It is desired state like the compose files: a change shows up in the plan (`~ ui: a -> b`) and takes effect on apply.
- The host keeps `~/.vops/config.yml`, a copy of the last applied `vops.yml` (the "lock"). The daemon always starts from the lock, never straight from the repo, so a broken or half-pushed `vops.yml` can't stop it: the plan warns "keeping the config in effect" and nothing changes.
- `vops install` sends the local `vops.yml` to the host as its first lock, so the daemon and the proxy start with the right ports and tls before the first sync.
- A hand edit of the lock is drift: the next plan shows it and apply puts `vops.yml` back.
- Listener changes need new sockets, and only the process that owns them restarts, by re-exec'ing itself (same pid, systemd doesn't notice; containers keep running): http, https, tls, acme email restart the proxy (sites blink for a moment), `ui` restarts the daemon (sites don't notice). After writing the lock the daemon tells the proxy to re-read it (`POST /reload`); the proxy compares with what it runs and decides. Everything else (domain, snapshots, preview limits) applies live, in both.
- Parsing is strict: a typo in `vops.yml` is an error, not a silently ignored key. Every key has a default, so a new key (like `image_keep`) absent from an existing `vops.yml` or lock changes nothing on upgrade.

## Snapshots and rollback

- btrfs subvolume snapshots, not copies or dumps: O(1), atomic per volume, copy-on-write, and database-agnostic. Anything with a journal (postgres, mysql/innodb, sqlite) recovers from a crash-consistent snapshot like from a power cut.
- Data dirs become subvolumes when vops creates them (empty volume `_data`, missing bind dir). A non-empty plain dir is never moved: it shows as "not covered".
- Rootless: files belong to subuids, and btrfs only lets the owner snapshot or remove a subvolume. Every btrfs op runs in `podman unshare` (the namespace podman itself uses). Deleting uses `property set ro false` + `rm -rf`, which unprivileged users may do since linux 4.18. No root, no `user_subvol_rm_allowed`.
- Snapshots live in `~/.vops/snapshots/<project>/<time>`, same filesystem as the data (btrfs can't snapshot across filesystems). Metadata in sqlite: `snapshots` (one moment) + `snapshot_volumes` (one row per volume).
- Pre-deploy snapshot whenever a project gets a create/update, of all its data, not only of the changed service: a migration job changes the db's data without redeploying the db. Running containers that use the data are paused (milliseconds) so all volumes are captured at the same instant. A failed pre-deploy snapshot aborts that project's deploy: deploying without the safety net must be a decision (`snapshots: off`).
- Data is found from both the containers' mounts (what runs) and compose (what should run), so a disabled project can still be snapshotted.
- Restoring data stops the project's containers, snapshots the current data as `pre-rollback` (undo point), restores each volume (the live one is moved aside and put back if the restore fails), starts what was running.
- Retention: newest `snapshot_keep` (5) automatic snapshots per project; manual and uploaded ones are never pruned.
- Backups are snapshots as files, not `btrfs send`: a .tar.gz (`vops-backup.json` first, then one dir per volume) opens anywhere, needs no btrfs on the other side, and a snapshot is already a consistent point to read from. Export runs GNU tar inside `podman unshare` per volume (subuid owners are plain uids there, so numeric owners, modes and xattrs survive) and Go rewraps the entries into one stream: nothing is buffered, on either side. Import is the reverse: Go reads the upload, checks each entry, and pipes the good ones to `tar -x` in the namespace, one new subvolume per volume, made read-only at the end. Checked in Go, before tar sees anything: the manifest is first, volume names are the project's data today (a subset is fine: restore puts back only those), no absolute paths or `..`, only files, dirs and links (no devices, fifos), hard links stay in their volume, nothing goes through or replaces a symlink of the archive (so an archive can't write outside its dir, whatever tar's own defaults). Any failure deletes what was extracted and records nothing. The result is a snapshot with reason `upload`, never pruned; restoring it is the usual data rollback, with its undo point. A full-data download is "snapshot now, then export it", so it is consistent too. Incremental `btrfs send` stays an idea for big data.
- Data rollback is per project, never per service: snapshots capture all of a project's volumes at one instant, and restoring only some would mix instants (a db that no longer matches its uploads). Proposed and rejected on purpose. Images can roll back per service (nothing is mixed: each service is one image).

## Rollback: images and data

- A rollback returns to "right before deploy #N": the images of the project's previous deploy row (what ran right before #N, the "from" side of #N's image changes) and #N's snapshot (data right before it). The same meaning a row's `snapshot_id` already has, so one id says everything and every timeline node offers the same action. No previous row: images aren't available for that point.
- `vops rollback <project>` without an id goes to right before the newest deploy that isn't a rollback ("undo the last deploy"). Running it twice targets the same point, so it doesn't ping-pong.
- Parts: images and data by default (whatever is available: a point without a snapshot rolls back images only, and says so); `--images`/`--data` restrict and fail if that part isn't available; `--service` restricts images (and can't go with `--data`: data is whole-project); `--snapshot id` restores any snapshot's data, images untouched. The dashboard dialog does the same with checkboxes; everything available is checked.
- Images roll back without git, by pinning: a `pins` row (project, service, image, digest, compose's image at pin time, the deploy that ran it). The plan runs the pinned `image@digest` instead of compose's image, like a preview override, so a pinned service has no pending change and "the host differs from git" stays quiet. Rewriting git instead (a revert commit on the host) was rejected: the host repo would diverge from every laptop, and a registry push (the usual way to deploy an image) has no commit to revert.
- Only what changes is pinned: a service whose target equals what compose asks for now loses its pin instead. So undo falls out of the same rule, and a rollback never leaves pins that do nothing.
- Only images with a digest can be pinned: own-registry images and pulled images with a repo digest (`repo@sha256:…`). Built images and `localhost/` images without one are skipped as "can't roll back without the code (git)", the rest still rolls back. See TODO.md for tagging built images per commit.
- Pins expire when a newer version arrives, because a pin is an emergency state, not a way to run production: a registry push that would redeploy the service (a tag it runs; not with `x-vops.watch: false`, not preview tags) drops the pin and deploys; an apply where the service's compose `image:` differs from the pin's recorded one (or the service is gone, or the project) drops it. Env, ports and other compose changes keep the pin and redeploy with the pinned image. Dropping one records an event; the plan shows it (`@ web: pin to #12 dropped (compose says … now)`).
- `vops unpin <project> [service...]` and the dashboard's Unpin remove pins and redeploy only those services (rolling). Other pending changes of the project wait for an apply, so an unpin never deploys something nobody reviewed.
- Previews ignore pins: they follow compose and their own overrides.
- Order: images only is an apply of the pinned services (preflight pull of every target first, rolling, no downtime, the usual pre-deploy snapshot). Both: preflight images, stop the project, `pre-rollback` snapshot, restore, set pins, start the unchanged services as they were and deploy the pinned ones. A preflight failure (image gone, pull fails) changes nothing.
- The rollback row records `before_id` (right before which deploy), `parts` (`images`, `data`, `images,data`; old rows are `''` = data), `restored_id`, and the images after, as usual. Undoing rollback R = rolling back to right before R with R's parts; `undoes` = R. The "pin only if different" rule makes this remove R's pins or put earlier ones back.

## Deploy history and the timeline

- `deploys` table: one row per project per apply that changes it (any action other than none, or a plan error), and one per rollback. Written by the engine (`applyProject`, `Rollback`), so cli, dashboard and registry pushes are all covered; the caller only names the trigger (`sync`, `apply`, `ui`, `push`, `unpin`; `rollback` is set by the engine). A no-op apply records nothing. Previews have no rows: the previews table is their record.
- The row is written when the deploy ends (no "running" state that a crash would leave behind). Recording never fails a deploy.
- `snapshot_id` is always the data right before that event: the pre-deploy snapshot for a deploy, the pre-rollback (undo) snapshot for a rollback. One meaning, so every node's "Restore data" and "Preview from here" start from the same place: the moment before it happened. The alternative (a deploy owns the snapshot taken by the next one, "its data at the end") needs the next row to exist and makes rollbacks a special case.
- Images: what runs after the event, per service, read back from podman: a service whose containers carry the desired hash runs the desired image (the hash covers our registry's digest; a pinned service records the pinned image with its original tag); otherwise (a failed update kept the old replicas) the previous row's entry is carried over. Digests: our registry's from the plan, pulled images' from `podman image inspect`, none for `localhost/` and built images (built ones are marked `built`: the commit rebuilds them).
- Own-registry images referenced by digest (`registry.<domain>/shop/web@sha256:…`, which is how a preview pins a past deploy's image) run the loopback pull ref directly: a digest can't be a local tag. So "Preview from here" gets exactly the bytes that ran, even after the tag moved.
- A rollback to right before an earlier rollback (or restoring its undo snapshot with `--snapshot`) records `undoes` = that rollback. The project banner "Rolled back to before #N (images, data) · Undo" shows while the project's newest row is a successful rollback that isn't an undo; the next deploy (or the undo) clears it. It comes from `last_deploy` in `/api/status`, so it shows on every tab and needs no extra polling.
- Retention: 5000 rows host-wide (a trigger, like events). The timeline shows the newest 100 deploys of a project; snapshots referenced by rows are shown on them, other snapshots (manual, or older pre-deploy/pre-rollback) are their own nodes. Pruned snapshots just disappear from their row ("no snapshot").
- Previews record `deploy_id`: the node they branched from (the node picked in the dashboard; for live data, the project's newest row at creation; 0 when made from a snapshot, which places them on the node showing that snapshot). The timeline shows them as chips there.
- The Data tab was folded into the timeline: coverage warnings on top, "Snapshot now" on the "now" node, delete on snapshot nodes. One place for "what happened to my data".
- Pins are visible everywhere a service is: `vops status`, `vops plan`, a "pinned · #N" badge with Unpin in the Services tab and the overview's list, and a warning on the overview. A forgotten pin would silently keep an old version in production.
- Code and compose rollback stay a git operation: the rollback dialog (and the cli plan) show the data's commit next to the running one and, when they differ, the exact commands (`git restore --source=<sha> --staged --worktree -- <project>/`, commit, `vops sync`). Git stays the single source of truth; a rollback that rewrote the host repo would diverge from every laptop. Images are the exception because they don't live in git: pins cover them.
- `/api/timeline?project=` returns everything the tab and `vops history` need in one call (rows, snapshots, image changes vs the previous row, preview chips, images gone from the registry, commit subjects via one `git log --no-walk`), so both render the same thing. `GET /api/rollback` is the rollback plan (the dialog and the cli confirmation print the same thing); `POST` runs it.

## SQL: sqlc, migrations, triggers

- sqlc (same config as golang-tmpl): SQL in `internal/store/queries.sql`, schema in `internal/store/migrations/*.sql`, generated Go committed in `internal/store/queries/`. The store package keeps only what SQL can't do (encryption, hashing, json repos) and the friendlier types. sqlc is a dev tool only: `go install` and the binary don't need it.
- Migrations run in name order, each once, in a transaction, tracked in `schema_migrations` (the golang-tmpl runner).
- The audit log is written by triggers on every table, so no code path can forget it. Triggers never copy secrets: env values, users' secrets (only "new password"/"new token") and session ids are left out (sessions show 8 chars of the id hash and their user). Retention is a trigger too (20k rows audit, 5k events).
- `events` (human-readable, written by code) and `audit_log` (every db write, written by triggers) are separate on purpose: one says "deployed shop/api", the other "projects.commit changed".

## Small ones

- Nothing deploys without an explicit apply: env changes, enable/disable and plain `git push` only show up as "pending" (cli `status`, dashboard banner). The exception is the registry push trigger, which is the point of it.
- `apply` from the cli shows the plan and then applies the exact commit it showed (`--commit`), so a push in between can't sneak in.
- A plan error in one project (bad compose, image not pushed yet) fails that project only; the others still apply.
- Env values, admin passwords and chosen tokens travel over ssh stdin, never as command-line args (no `ps`/history leaks).
- The unix socket lives in `~/.vops/`, so the home path must be under ~100 chars (unix socket limit). Real homes are.
- Dashboard logins are serialized and a failed attempt costs 1s (plus pbkdf2 600k): slow for brute force, no lockout to abuse (per-IP backoff is in TODO.md).
- Registry basic-auth results are cached for 5 minutes (pbkdf2 per blob request would be slow); every user change (role, global, repos, secret, delete) clears the cache, so a deleted user or an old token stops working at once.
- HTTPS listens even before a domain exists (the domain arrives with the first sync); until then port 80 serves plain http.
- Every `podman.Run` has a timeout (2m + the `-t` grace period; 30m for pull/build): a hung podman (storage lock, dead mount) would otherwise hold the deploy lock forever and block every apply and restart. Log streams are exempt.
- The daemon crashing doesn't touch containers (`KillMode=process`, systemd restarts it in 2s, routes are rebuilt from labels) nor the sites (the proxy is another process). Only the dashboard and the registry are down for those seconds: the proxy answers 502 with a clear text for their hosts.
- Tests share one isolated podman storage (`~/.cache/vops-test`) guarded by a file lock, so `go test ./...` runs packages in parallel safely.
- The daemon idles at ~16MB RSS.
- The systemd units set `HOME` explicitly (system units have none) and `StartLimitIntervalSec=0` (never give up restarting).
- Containers get `--log-driver journald` explicitly when journald is running: some distros (Fedora's podman image) default to k8s-file, which loses logs of removed replicas.
- Removing a container counts as done when it is gone, even if podman errors cleaning up its network afterwards (seen with nested podman).
- Changing only readiness settings (`health`, `timeout`, `strategy`) doesn't recreate containers; they aren't part of the service hash.
- Fuzz tests (`FuzzSplitPath`, `FuzzLoad`) run their seed corpus in every `go test`; `go test -fuzz` explores. The registry path splitter and the compose loader are what the network and git feed.
- `just vps-test` is the production-like check: fake ssh in `go test` covers the logic fast, the vps container covers real sshd/systemd/root.

## The proxy process

- `vops proxy` owns :80/:443 from the config lock, autocert (same `~/.vops/certs`, same host policy: `vops.<domain>`, `registry.<domain>`, routed hosts), http→https redirects, HSTS and the routing table. It imports `config` and stdlib only: no sqlite, podman, registry or deploy engine, so there is little in it to crash.
- The daemon has no public listener anymore. It keeps `vops.sock` (cli) and `ui` (loopback by default: `vops ui` tunnels and podman pulling from our registry), and serves `vops.<domain>` and `registry.<domain>` on `web.sock` (0600), where the proxy forwards them with a plain `httputil.ReverseProxy`: request and response bodies stream (registry pushes, log follows), no size limits, no read/write timeouts (only 10s for headers). The daemon trusts the forwarded client ip and scheme there (login events, `Secure` cookies). Daemon down → those two hosts answer 502 "the daemon is not running", every site keeps working.
- Protocol, on `proxy.sock` (0600, http): `PUT /routes` swaps the whole table and answers after the swap, `GET /status` (proxy.Version, vops build, route count, table hash, pid, last push, 429/413 counts per project), `GET /routes`, `POST /reload` (re-read the lock), `GET /ping`.
- The daemon stays the source of truth (routes rebuilt from podman labels). Every change of its table (`proxy.Table.OnChange`) sends the whole table, synchronously: a rolling release's switch returns after the proxy swapped its map, so drain-then-stop stays correct. Whole table, not diffs: tables are small, and a push can't be half-applied or out of order (pushes are serialized and always send the current table). The housekeeping tick (every minute) rebuilds from podman and resends, so drift heals by itself.
- Proxy unreachable during a deploy: the deploy goes on (the proxy keeps serving its last table), the daemon logs it and records an event, and resends every second until the proxy answers (and records that too).
- The proxy writes `routes.json` (write, fsync, rename) after each push that changes it, and loads it at start: it comes back with the right routes after its own restart even with the daemon dead. One writer, the proxy: the file is exactly what it last served. If the daemon wrote it instead, the file and the proxy's memory would be two copies with two writers, and a proxy that missed pushes while down would still need the daemon's retry, which already covers it.
- `proxy.Version` (an int) is the proxy's behaviour plus this protocol. Bump it when either changes, and only then: that is what makes `vops setup` restart the proxy. A daemon change never needs it.
- Limits (`x-vops` `rate`, `burst`, `max_body`, top level of compose) are per project, in the routing table (`limits` on each route; `omitempty`, so tables without limits hash the same). They live in git like everything else (no dashboard-only toggle: that would be drift); an emergency override table is still an idea (TODO.md). Apply records them in `projects.limits` and the table is built from podman labels plus that column, so a change is its own plan line and never recreates containers (labels would have, or gone stale). Previews use their project's. The proxy keeps a token bucket per (project, client ip) in memory, purged after 10 idle minutes; the client ip is the tcp peer (the proxy is the edge; `X-Forwarded-For` is the client's own text). `max_body` refuses on `Content-Length` and cuts chunked bodies with `http.MaxBytesReader` (the ReverseProxy error becomes `413`). Sizes are 1024-based (`10MB` = 10485760 bytes), like podman's and most people's intuition for upload limits. 429s and 413s are counted per project in `GET /status`. The dashboard and registry hosts are forwarded before routing, so they are never limited.
- Visibility: `/api/status` has `proxy` (up, version, routes, in sync = the table hashes match), and adds a warning when it is down, out of sync or on another version. `vops status` prints it on the first line; the dashboard shows it in the top bar and the warnings on the overview.

## Versions: cli vs host

- The cli sends its version with every forwarded command (`VOPS_CLIENT=v1.3.0 ~/.vops/bin/vops --local ...`: an env assignment, so hosts from before the check just ignore it). The host refuses when major.minor differ, exit code 3: older cli → "update yours (go install ...)", newer cli → "run `vops install` to upgrade it". Patch differences are fine; `version` always answers; `setup` is exempt (install already decided). Dev builds (no parseable version) skip it with a one-line warning. Versions come from `-ldflags -X main.version` or the module/VCS version Go stamps (`v1.2.1-0.2026…+dirty` counts as 1.2).
- No extra ssh round trip per command for this. A newer cli against a host from before the check can't be caught by the host; `sync`/`apply` catch it anyway: their plan carries the host's version since 1.3, so a plan without one is a 1.2-or-older host.
- `vops install` reads the host's version in its probe and prints "installing", "upgrading vX → vY" or "reinstalling vX". Installing an older major.minor over a newer host is refused unless `--force` (a teammate with an old cli would otherwise downgrade production). With `--binary`, the version is asked from that binary (or read from its build info when it's for another arch).

## Previews

- A preview is the synthetic project `<project>@<name>`, run by the same engine (labels, hashes, plan/apply, rolling releases). `@` can't be in a dir name, so it never clashes with a real project. Names: slug `shop--pr-42` for podman objects (a dir could produce that slug, so `preview up` refuses a name whose slug or dns name belongs to an existing project), domain `<service>.pr-42.shop.<domain>`, which autocert already handles.
- Previews are not in the plan: git doesn't describe them. `Plan` ignores containers of `@` projects (else they'd be "removed from git"); the `previews` table is their desired state (commit, image overrides). No pre-deploy snapshots of them, no `projects` row.
- Code: a detached git worktree of the host repo in `~/.vops/previews/<slug>`, at the project's applied commit (or `--ref`). It gives each preview its own bind paths, build contexts, `env_file`s and `preview.env` at that commit, with no copying. The commit is pinned: later pushes and syncs don't move it, `preview up --ref` does. `vops preview up --ref <branch>` pushes a local branch to the host first (never `main`), so `--ref` just works from the laptop.
- Data: only the volumes and binds (inside the project dir) of `x-vops.preview.copy` services, copied once, at creation, as writable btrfs snapshots straight from the live subvolumes (the project's containers are paused for the milliseconds it takes, like a pre-deploy snapshot). No snapshot row is recorded, so previews never push pre-deploy snapshots out of retention. `--from <id>` copies a recorded snapshot instead. Updates keep the preview's data; to start over: `rm` + `up`. Volumes map by compose key (`vops-shop-db` → `vops-shop--pr-42-db`), binds by path inside the project dir (into the worktree). Everything else starts empty; a volume a copied service shares with another running one is copied (the plan warns). A service added to a preview later (a push of another declared service) starts empty: the copy is made once. Without btrfs a preview starts empty.
- Env: two layers only, never production's env: `preview.env` in the project dir (committed, not secret: `SMTP_HOST=mailpit`), then preview secrets (`vops env set shop --preview KEY`) on top. The copied data still carries production's own credentials (db passwords): set what the preview needs with `--preview`. Preview secrets live in the `env` table under project `<project>@*`: same encryption, same write-only api, same audit, no new table. `COMPOSE_PROFILES` comes from these layers; `VOPS_PREVIEW` is set.
- Guardrails are defaults, not options: no shared `vops` network (a service asking for it gets the preview's default network), only declared services run (below), no published host ports (they'd clash with production), no `x-vops.domains` (they're production's), `name:` of volumes and networks ignored (it would be production's object), external volumes used by running services are an error. External networks and absolute bind mounts are kept (the plan warns about the latter): they are explicit infrastructure.
- Limits: `preview_max` (5) previews on the host, counted from the table; `preview_ttl` (3d) since the last `up` or push. Housekeeping checks every minute. Both live in `vops.yml` like everything else.
- Opt-in per service (`x-vops.preview: {with, copy}`), not per project with opt-outs (the old `x-vops.previews` pattern + `preview.skip`). A preview carries production data, so what runs and which data is copied must be written down: a new worker, cron or database added to the compose doesn't silently start in every preview on a copy of production. `copy` is explicit and separate from `with` because copying is the risky part (personal data, queued jobs); `copy` implies `with`, since copied data nobody runs is useless. What a preview runs: the services it is for, plus their `with` and `copy`. "The services it is for" is stored (`previews.services`): the services pushed or given with `--image`, accumulating like the image overrides; empty means every declared service (a plain `preview up`, "New preview", "Preview from here"), and such a preview stays that way when pushed to, so it never shrinks. Images of a timeline node are pins, not what the preview is for; overrides of services that don't run are ignored for them, an error for `--image`. A required `depends_on` outside a declaration's set is a compose error (it used to be dropped silently, which gave previews that start and fail at runtime). Not transitive: a `with` service's own declaration doesn't pull more in; name it.
- Registry trigger: a fixed tag prefix `preview-` (no per-project pattern: one rule to learn, and the tag-deletion idea can match it). A pushed `preview-<name>` creates or updates preview `<name>` in every project where a service running that repo has `x-vops.preview`; services running it without one are skipped with an event. The image keeps its registry host and gets the pushed tag. Overrides accumulate, so `shop/web:preview-pr-42` then `shop/api:preview-pr-42` is one preview with both declarations. A `preview-*` tag is never a production redeploy, even if production runs that exact tag.
- `rm` removes containers (and their anonymous volumes), networks, volumes, built images and local tags of the overrides, then the worktree with its data, then the row. If a step fails the row stays, so a retry or the ttl finishes the job. Registry tags stay (they're the user's pushes).
- Removing a container also removes its anonymous volumes (`podman rm -v`), for previews and projects alike: an image's `VOLUME` (postgres has one) left one volume behind per removed job or replica, forever.
- Preview lifecycle events are recorded under the base project (kind `preview`), so `vops events shop` shows them; deploy lines use the preview path.
- Dashboard: Previews tab per project, previews as subtle rows under their project in the sidebar and a count on the overview. The "copy of production data" warning is shown once, on top of the tab, not per preview. The empty state explains the `preview-*` push with a command built from the project's own declared images; with no declaration it shows the `x-vops.preview` snippet to add, built from the project's services (`preview` on each service in `/api/status`). Preview logs are `/api/logs?project=shop@pr-42` (same labels and journald tag scheme as projects) on the full-page log view.
- The Environment tab switches between production and preview secrets (`?scope=previews`), with one line saying previews don't inherit production's env and read `preview.env` from the repo.

## Secrets backup (.secrets.age)

- Git rebuilds everything but env secrets, which live only in `~/.vops/vops.db` sealed with `secret.key` on the same disk. So the repo gets `.secrets.age`: age, armored, a sorted commented .env per project and scope (`[shop]`, `[shop previews]`, Go-quoted values so newlines survive). age because it encrypts to ssh public keys (`agessh`): the people who can deploy can decrypt, with the key they already have, and nobody learns a new concept. Users never run age; `age -d -i ~/.ssh/id_ed25519 .secrets.age` works as an escape hatch.
- Named `.secrets.age` at the root (not in a project dir, so it is never part of a project's files or plan). Repos that ignore dotfiles (`**/.*`) would drop it, so the cli checks `git check-ignore`, adds it with `-f` and prints the `!/.secrets.age` line to add.
- Recipients are computed on the host, not configured: the vops user's `authorized_keys` (read live: whoever can deploy), root's (hosting panels inject their key there; the daemon is rootless, so `vops setup` copies it with `sudo -n`, never a password prompt, never writing anything under `~/.ssh` or `/root`; without sudo the last copy stays), and `secrets.recipients` in `vops.yml` (desired state: a plan line, effective on apply). Only ed25519 and rsa work with age: others (ecdsa, `sk-*`, `cert-authority` lines) are listed as skipped with the reason. Options (`command=`, `from=`) are parsed by `ssh.ParseAuthorizedKey`. Duplicates count once.
- The host encrypts (it has the plaintext and only needs public keys) and keeps the latest blob in `~/.vops/secrets.age`. age output is random, so it re-encrypts only when an HMAC (key derived from `secret.key`, never a plain hash of secrets) of plaintext + recipient keys differs from the one in `meta`. Checked after every env write (cli, dashboard, preview secrets, rm, restore), on vops.yml apply, at start, every minute (authorized_keys edits) and whenever someone asks for it.
- No usable recipient: no new backup. The previous one stays and the warning is in `vops status`, the dashboard and every sync. No secrets ever: no file at all.
- The host never commits (its repo is the push target; commits there would diverge from every laptop). The cli commits only that path (`git commit --only`, so the user's staged work stays staged): `vops env set/rm` right away, `vops sync` after its pull and before its push, so a dashboard change reaches git on the next sync; status says "behind" meanwhile. A merge whose only conflict is `.secrets.age` (two laptops committed different versions) takes either side: sync writes the host's latest right after.
- A copy in git that this host didn't write is never replaced while it holds secrets the host lacks: the host lists the sha256 of every blob it wrote (`secrets.known`), so "older version of ours" (replace it) and "another host's" (a new or reinstalled host: restore first) are told apart without decrypting. Otherwise a fresh host's first sync, or an `env set` before it, would overwrite the only backup with an almost empty one. Sync offers the restore (`[Y/n]`, `-y` = yes, no terminal and no `-y` = a warning); declined or undecryptable, the file stays and sync goes on. `vops env restore [file]` does it explicitly. `git rm .secrets.age` starts over.
- Restore decrypts on the laptop (private keys never go to the host): the `--ssh-key`/lock key, then `~/.ssh/id_ed25519`, `id_rsa`, other `id_*`; encrypted keys ask their passphrase (no echo) only when the backup is encrypted to them. ssh-agent can't do age's key exchange, so a key only in the agent is reported as such. Values travel as the same plaintext over ssh stdin (never argv, never a file) to a socket-only route that sets missing keys with `INSERT … ON CONFLICT DO NOTHING`: existing values always win. Each restored key is an event.
- History is the limit: a removed key still opens old commits. Documented (rotate secrets when removing someone) rather than worked around: rewriting history is not ours to do.

## Notifications

- Web Push, implemented with the stdlib (VAPID: an ES256 JWT, RFC 8292; payloads: aes128gcm, RFC 8291, `crypto/ecdh` + `crypto/hkdf` + AES-GCM), tested against the RFC's test vector. No ntfy/Pushover/Firebase account: the browser vendors' push services are the only third party, and they only see ciphertext. Outbound webhooks are the next step (TODO.md).
- Nothing in `vops.yml`, on purpose: who gets what and on which device is per person, not desired state of the server, and thresholds are tuning, not config worth a plan line and a review. Everything lives in the db (`push_subscriptions`, `alerts`, `notify_prefs`, `notify_settings`) with audit triggers, and is edited from the dashboard. Defaults are chosen so that nobody needs to touch them.
- The VAPID keypair is generated once and kept in `meta` (`vapid_private`). It is not in the secrets backup: losing it (a new host) only means every device subscribes again with one click, while backing it up would put one more private key in git history.
- JWT `sub`: `mailto:<email>` from `vops.yml` (the ACME email), else `https://vops.<domain>`, else `mailto:vops@localhost`. Push services want a contact; none of them requires it to be reachable.
- iOS only delivers Web Push to web apps added to the home screen, so the dashboard has a manifest (`display: standalone`, PNG icons) and the page says so on iOS. The service worker (`/sw.js`, root scope, no caching) only shows notifications and, on click, focuses a dashboard window and sends it to the alert's page (`postMessage`; `navigate()` only works on controlled clients). `localhost` is a secure context, so `vops ui` works too.
- An alert is a row with a key (`restart:shop/web`, `down:shop/web`, `resources:disk:/home`, `oom:host`) and at most one live (`ended_at = 0`) per key, a unique partial index. States: open (being sent), silenced (by someone, for everyone), expired, resolved. Silenced and expired stay live until their condition ends, so they don't reopen the next minute. Every new alert is also an `events` row (kind `alert`). Retention: 2000 rows (a trigger, like events).
- Repeat and expire (1h, 24h): a down site that nobody acts on keeps reminding, but not forever; a forgotten alert costs one push an hour for a day, then nothing. Event kinds (deploy failed, restart, oom) coalesce on their key: a crash loop is one alert with a count in its title, re-sent on the repeat schedule, not per crash; it ends after 30 quiet minutes. Condition kinds (down, health, resources) end when the detector stops seeing them for 3 cycles. The state machine is one pure file (`notify/alert.go`, time injected), unit tested.
- Resolved notifications exist but are off by default: they double the pushes for little, and the dashboard shows the state anyway. Successful deploys likewise (off); a successful deploy ends the project's `deploy_failed` alert.
- Container deaths come from `podman events --filter event=died` (instant; reconnects with backoff), each judged 3s later: vops' own stops are not alerts. The engine marks every container it stops, removes or restarts (apply, rolling releases, rollback, restart, previews, network recreation; the mark lives 10 minutes and one death consumes it), a container gone by then was removed (only vops removes them), jobs are meant to exit, previews aren't watched, and nothing is judged once the daemon is stopping (a host shutdown kills everything). The stream can miss deaths (reconnecting, podman restarted), so housekeeping reconciles every minute: restart counts and finish times against the previous pass, minus what the stream saw; a pass during which the engine moved containers only re-baselines. Lock-based suppression alone ("ignore events while deploying") was rejected: the engine lock is global, so it would hide real crashes of other projects during long deploys.
- `podman kill` (SIGKILL, exit 137) raises a restart and an oom alert: from outside, a SIGKILL looks the same whether a person, the kernel OOM killer, systemd-oomd or earlyoom sent it.
- Down and health: a probe every 30s per routed service of enabled, non-preview projects (`x-vops.health` if set, else a TCP connect to its 127.0.0.1 port; compose healthchecks with `podman healthcheck run`, as readiness does), `down_after` (3) failures in a row. A round that overlaps an engine operation (a generation counter bumped when one starts and ends) is thrown away and keeps the live alerts alive: a deploy is not an outage.
- Resources: sysmon samples every 30s in the background now (the System page shares the samples). Containers are read straight from cgroup v2 files (`memory.current/max/events`, `cpu.stat/max`, path from `podman inspect`, works rootless), not `podman stats` every tick. Host oom kills come from `/proc/vmstat` `oom_kill`, containers' from `memory.events`.
- Early killers: on rootless hosts systemd-oomd watches `user@.service`, which holds the daemon, the proxy and every container, and may pick the proxy; earlyoom picks the biggest process. Unprivileged units can't lower their `OOMScoreAdjust`. So vops warns before they act (PSI `some avg60` > 20%, memory available < 10%) instead of changing the containers' `oom_score_adj`: that flag is part of the service hash, so setting it would redeploy every service on upgrade.
- Access: one function, `notify.CanSee(user, project)`: global users see everything; others the projects whose services run one of their repos; host-wide alerts only global users. Today only admins (global) log in, so it is future-proofing for roles, used by the sender, the alerts list and the badge.
- Anyone logged in can silence any alert and remove anyone's device: the people who can log in are the same small team, and a stale device (a lost phone) must be removable by whoever notices.
- Sends run in background goroutines with a 10s timeout per push service, `TTL` = the repeat interval (capped at 24h), `Urgency: high` for down and oom. A 404/410 deletes the subscription (an event says so); other errors are shown on the device row.
