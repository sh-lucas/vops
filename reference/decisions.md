# Decisions

Every non-obvious choice made while building vops, with the reason. Newest last. If you change one, update it here.

## Shape

- **One binary, `vops`.** Local CLI, remote CLI, daemon (`vops daemon`) and proxy (`vops proxy`) are the same binary. Install = copy it over ssh. No scp, no rsync: `ssh host 'cat > file' < binary`.
- **Go deps: 4.** `modernc.org/sqlite` (pure Go, keeps the binary static), `go.yaml.in/yaml/v3` (compose files; a YAML parser is not worth writing), `golang.org/x/crypto` (autocert, ssh key parsing), `filippo.io/age` (the secrets backup, pure Go). Everything else is stdlib.
- **Runtime deps on the host:** linux, systemd, podman (netavark backend), git. btrfs (+ btrfs-progs) enables snapshots and rollback; without it everything else works and the dashboard says why snapshots are off.
- **Our own reverse proxy, in its own process.** No Caddy/Traefik/nginx: rolling releases need to flip traffic the moment a new replica is ready, and ours does it with a map swap instead of a config reload. TLS from autocert (HTTP-01 + TLS-ALPN-01). It runs as `vops proxy` (`vops-proxy.service`), not inside the daemon: a panic, OOM, deadlock or upgrade of the daemon used to take every site down. See "The proxy process".
- **The CLI talks to the host through ssh only; the dashboard and the registry are the web-facing parts.** `vops status` locally runs `ssh host ~/.vops/bin/vops status`; the remote vops talks to the daemon over a unix socket (`~/.vops/vops.sock`). ssh is the CLI's auth. The network-facing surfaces are the dashboard + api (`vops.<domain>`, admin password + session cookie), the registry (`registry.<domain>`, basic auth: admins' passwords, deployers' tokens) and the apps' routes. Deploys (`sync`, `apply`, `install`) never go through the web; once logged in the dashboard can apply, rollback, manage env, users and previews.

## Git sync

- `~/vops` is a normal (non-bare) repo with `receive.denyCurrentBranch=updateInstead`: a `git push` updates the working tree, no hooks, no checkout step. It refuses if someone edited tracked files on the server, which is wanted.
- `vops sync` = `git pull vops main` → `git push vops HEAD:main` → remote `vops plan` → show → confirm → remote `vops apply --commit <sha>`. Apply refuses if the remote HEAD moved since the plan.
- Plain `git push vops` works too; nothing deploys until `vops sync`, `vops apply` or the UI's "apply" button (which shows the pending plan first).
- `vops-lock.yml` (gitignored) holds `host`, `port`, `ssh_key`. `--host`/`--ssh-key` override it, so CI needs no file.

## Projects & compose

- A project is any git-tracked directory with `compose.yml`, `compose.yaml`, `*.compose.yml` or `docker-compose.yml`. Several compose files in one dir are merged (duplicate service = error). Nested dirs are separate projects.
- vops parses compose itself and calls `podman run`. No podman-compose/docker-compose: they can't do rolling releases and are one more dependency. Unsupported keys are an **error**, never silently ignored.
- Project `a/b` gets domain `b.a.<domain>`. A routed service gets `<service>.b.a.<domain>`, plus `b.a.<domain>` if it is the project's only routed service. Extra domains via `x-vops.domains`. Routing is opt-in per service with `x-vops.port` (the HTTP port inside the container).
- Default `restart: unless-stopped` (compose's `no` is a bad server default).
- Interpolation (`${VAR}`, `${VAR:-x}`, `${VAR:?err}`, `$$`) uses the project env vars stored by vops, not the shell. `environment: [KEY]` passes the project var through.

## Networking

- Each project has network `vops-<project>`; services resolve each other by service name.
- Every container also joins the shared network `vops` with alias `<service>.<project reversed>` (e.g. `db.sub.proj`), so any project reaches any other by a predictable name.
- The proxy reaches containers through a port published on `127.0.0.1:<port>`; vops picks it (stable across restarts). Same rootless or rootful.
- netavark is required (aliases + DNS); CNI setups without dnsname don't resolve names.
- Compose `networks` work like compose: none = project `default` + shared `vops`; some = exactly those. `vops` is a reserved key, so a service can opt in explicitly and a db on an internal network stays invisible to other projects.
- Networks carry a `vops.nethash` label (hash of their definition). A changed definition = remove the project's containers on it, recreate, redeploy (podman can't alter a network). The default network created before networks were configurable has no hash; it is accepted while still a plain bridge, so upgrading restarts nothing. Service hashes include the hashes of their networks, so a network change redeploys its services.

## Deploys

- Desired state = git + env vars. Actual state = podman containers with `vops.*` labels. The db is not the source of truth for containers; the daemon rebuilds its routing table from podman on start.
- Each service has a hash of everything that defines it (resolved args, image, own-registry digest, build context tree hash). Different hash = redeploy. An unchanged service's hash must stay the same across vops versions or an upgrade redeploys everything (`TestServiceHashIsStable` guards it; migrations are additive for the same reason). Readiness settings (`health`, `timeout`, `strategy`) are not in it, so changing only them recreates nothing.
- Strategy: `rolling` for routed services (new replicas → readiness → switch traffic → drain 2s → stop old), `recreate` for the rest (two postgres on one volume loses data). Override with `x-vops.strategy`.
- Readiness: compose `healthcheck` (vops runs `podman healthcheck run` itself, no systemd timers) → `x-vops.health` HTTP path → TCP connect on the routed port → "still running after 2s". Failed readiness removes the new replicas (after printing their last logs; journald keeps the rest) and keeps the old ones. With `recreate` the old ones are already gone, so the service is down until fixed; that beats a failed replica staying and being routed by the next `RefreshRoutes` (it only looks at running containers and labels), because nobody would notice.
- `build:` builds on the host, tagged with the git tree hash of the context, so it rebuilds only when the context changes.

## Registry (own implementation)

- OCI distribution spec, stdlib only, filesystem storage: `blobs/sha256/<ab>/<digest>`, `repos/<name>/tags/<tag>` (file with the digest), `repos/<name>/manifests/<digest>` (empty marker), `uploads/<uuid>`.
- Auth is HTTP Basic over HTTPS, two roles in the `users` table. Admins log into the dashboard and push/pull every repo with their password (pbkdf2, 600k). Deployers never log in; they get a random token (stored as sha256: high-entropy tokens need no slow hash) and push/pull every repo (`global`) or those in `user_repos`. Push and pull are one permission: a CI that pushes also pulls its base, and a pull-only token proved a distinction nobody used.
- This replaced "the dashboard admin pulls everything, pushes nothing" and the per-user regex: an admin could create a user that pushes anything, so refusing its own pushes only added a second credential; a regex is a footgun (`shop.*` matches `shopping/x`) and exact names cover every real case. The migration turns `.*`/`.+` into global, json repo lists into rows, drops any other regex with an `auth` event naming the user, and makes the old dashboard password the `admin` user.
- Repo names are normalized in Go (trimmed, everything after the first `:` dropped so `shop/web:latest` is `shop/web`, deduped); the db refuses a `:` or an empty name anyway.
- The rules live in the db so no code path can break them: `CHECK`s (role is admin or deployer; admins are global; admins' secrets are pbkdf2 `salt:key`, deployers' aren't), `RAISE(ABORT)` triggers (the last admin can't be deleted or demoted; a global user can't get repos) and cascades (setting global deletes the user's repos; deleting a user deletes its repos and sessions; a demotion or new secret deletes its sessions). `PRAGMA foreign_keys` is on for every connection (the dsn), so cascades are real.
- `vops-internal` is reserved (a `CHECK`): the daemon's own loopback pull user. The daemon pulls its images through the loopback UI listener with an in-memory token, then tags them with the public name, so deploying its own images needs no DNS/TLS.
- Basic-auth results are cached 5 minutes (pbkdf2 per blob request is slow); every user change (role, global, repos, secret, delete) clears the cache, so a deleted user or old token stops working at once.
- GC removes an empty repo's own `blobs`/`manifests`/`tags` and then only empty dirs: a repo nested under it (`shop/web` under `shop`) stays.
- Atomic writes go through dot files (no tag or digest starts with a dot): listings skip them without hiding a tag like `v1.tmp2`; gc drops those a crash left.
- Watchtower replacement: pushing a tag a service uses redeploys it (rolling). Opt out with `x-vops.watch: false`.
- GC is mark & sweep: untagged manifests (not referenced by a tagged index or as the subject of a kept one) and unreferenced blobs go; anything younger than 1h stays so pushes in progress are safe; uploads older than 24h are dropped. Runs daily, from `vops registry gc` and from the dashboard.
- GC also keeps a given set of digests: what pins run, previews' overrides by digest, and every image of the newest `image_keep` (10) deploy rows per project. Re-pushing `latest` leaves the old digest untagged; without this, image rollback and "Preview from here" break at the next gc. Counted in deploys, not days, because rollback is "the last few versions" whatever the release pace. Older rows keep showing, marked gone; rollback skips them with that reason.

## Logs

- Containers use podman's `journald` log driver, tag `vops.<project>.<service>`, passed explicitly when journald runs (some distros, e.g. Fedora's podman image, default to k8s-file, which loses logs of removed replicas). journald gives aggregation, rotation, compression, indexing and history across replicas. Reading = `journalctl`, falling back to `podman logs`.
- Search is `journalctl --grep` (PCRE2 builds; text regex-escaped, case-insensitive): reads backwards until n matches, so it covers the whole history without loading it. Without PCRE2, go filters the last 20k lines.
- Paging: every response carries `X-Vops-Before`, the journald cursor of its oldest line; `?before=<cursor>` returns the n lines before it (`journalctl -r --after-cursor`), loaded by the dashboard on scrolling to the top. No header = start of logs. Following = read to the end, then `-f --after-cursor=<newest>` (no gap, no "silence means caught up" guess); the dashboard keeps at most 5000 lines while following (Reload to browse history again).
- Date filter: `?since`/`?until` (unix seconds) map to `journalctl --since=@n`/`--until=@n`; a set `until` closes the range, so no follow. `X-Vops-First`/`X-Vops-Last` (first page only) give the journal's whole range for these services regardless of grep/since/until, for "logs available from X to Y". From/to are a date input plus an optional time input (empty = 00:00 / 23:59), because `datetime-local` yields no value until every field is filled.
- The dashboard downloads what is in view as `<project>[-<service>]-YYYYMMDD-HHMM.txt` or `.csv` (time, service, message; split in the browser).
- Lines carry the host's local time as text (the cli runs on the host); `X-Vops-Offset` (UTC offset, seconds) lets the dashboard rewrite them to the browser's zone, that of its from/to inputs.
- DuckDB/parquet rejected for now: needs cgo and a ~30MB library, breaking "static binary, few resources". Revisit if searching months of logs becomes a real need.

## Web UI

- Plain HTML + CSS + vanilla JS, embedded with `embed`, same JSON API as the socket. No build step, libraries, external fonts or CDNs (works offline). Everything is rendered with `h()` (never `innerHTML`).
- Layout: fixed sidebar (nav + project tree with a status dot: green running, amber pending/partial, red failing/invalid, grey disabled), a top bar with the host's commit, domain and a "pending changes" badge that opens plan/apply from any page. Below 880px the sidebar is a drawer. Light/dark follow the system. The shell polls status every 10s (sidebar, top bar, alerts badge); pages subscribe instead of polling.
- Project page = header + tabs (`#/p/<path>/<tab>`: services, timeline, previews, logs, env, events); a tab is one entry in `TABS` in app.js. Old links (`#/p/<path>`, `#/p/<path>/data` → timeline, `#/logs/<path>?service=x`, the full-page log view) keep working.
- System page (`#/system`, `/api/system`): read from `/proc` and `/sys` (no dependency, works rootless), no history. Rates and percentages are deltas against the previous sample, kept in the daemon: the first request samples twice 250ms apart, requests under 1s apart share a result (as does the notifications' 30s background sampling), so the page polls every 3s (15s in a background tab) for a few file reads. Disk io % busy = `io_ticks` of whole devices (`/sys/block`, minus loop/ram/zram); network counts physical links only (those with a `device`; bridges and veths would count bytes twice), all but `lo` if none has one; link % only when `/sys/class/net/*/speed` knows it. Disk space is per filesystem holding `~/.vops` and the repo (merged if shared). PSI rows hide without `/proc/pressure`. Host and daemon uptime live there.
- Events: 50 per page, "Load more" pages back by id (`/api/events?n=&before=`) so new events don't shift pages. `vops events` asks for 100.
- Streamed actions started from a dialog (rollback, unpin, preview up) show progress in a modal, like apply; closing it doesn't stop them. Destructive actions ask through an in-page `<dialog>` stating the consequences, not `confirm()`.
- Served on the `ui` listen address (default `127.0.0.1:9984`) and on `vops.<domain>` over HTTPS. Loopback by default (plain HTTP with a password over the internet is bad); `vops ui` opens an ssh tunnel and the browser; `ui: ":9984"` in `vops.yml` exposes it.
- Sessions: random id in an `HttpOnly; SameSite=Strict` cookie, sha256 stored in sqlite with its user (shown in the top bar, named in events). Mutating requests also need `X-Vops: 1` (CSRF without tokens). Only admins log in; a deployer's right token gets the same answer and event as a wrong password, so login can't tell which names are deployers. Housekeeping purges expired sessions.
- Env values are write-only: the API cannot read them back.
- Json request bodies are capped at 1MB (`413`; `400` for malformed json); the backup upload is the one unbounded body, streamed and checked as it arrives. A test walks every web api route and expects `401` without a session and `403` without `X-Vops` on mutating ones, so a new route can't forget either.
- The env view (`/api/env/usage`, `vops env ls`) reports names and sources only, never values, not even of compose literals. It is computed by the same `compose.Load` + env merge the plan uses (the interpolator records which `${VAR}`s each entry uses), so it can't drift from what podman gets. A compose literal whose key matches `PASSWORD|SECRET|TOKEN|KEY|PRIVATE` (case-insensitive) is flagged (committed to git; fix: `environment: [KEY]` + `vops env set`). A key nothing references (`environment: [KEY]` or `${KEY}` anywhere in the files; `COMPOSE_PROFILES` counts as used) shows as unused.

## Install

- `vops install user@host` checks arch/podman/git/systemd and the host's vops version, uploads the binary and runs `vops setup` there: creates dirs, inits `~/vops`, writes the two systemd units, enables linger (non-root), restarts the daemon, (re)starts the proxy if needed and, with no admin yet, creates `admin` and prints its password once. Running it again is the upgrade; there is no other command to learn.
- root → system units in `/etc/systemd/system/`; non-root → user units, needing `net.ipv4.ip_unprivileged_port_start<=80` (setup prints the sudo command if not).
- `vops.service`: `KillMode=process`, so restarting the daemon never kills containers. `vops-proxy.service`: no children, default kill mode, `RestartSec=1`. Both set `HOME` explicitly (system units have none) and `StartLimitIntervalSec=0` (never give up).
- Setup always restarts the daemon (new code) but the proxy only when it isn't running, its unit file changed, or it reports another `proxy.Version` over `proxy.sock`: restarting it is the only thing that interrupts sites. The binary is replaced with `mv`, so a running proxy keeps its old inode, which is fine: its behaviour is what `proxy.Version` describes.
- Order: daemon first, then proxy. From v1.2 (one `vops.service` holding :80/:443) the restarted daemon no longer binds them, so the proxy finds them free; if not (slow stop) it exits and systemd retries every second, forever. Then setup asks the daemon to send its table (`POST /api/proxy/sync`) so the first start serves every route within a second or two. That migration costs a few seconds of downtime once, and setup says so.
- Both units are `Type=notify` (READY=1 once sockets are bound, so `systemctl restart` returns when the process really serves) with a watchdog (`WatchdogSec=60` daemon, `30` proxy). The ping is sent only while a request to the process's own unix socket succeeds, so a deadlocked process is restarted (SIGABRT: Go prints every goroutine to the journal), not only a dead one. The daemon says READY before starting stopped containers after a reboot, so a slow podman can't hit the start timeout (its socket answers meanwhile; applies wait for the engine lock). sd_notify is ~50 lines of stdlib (`internal/sdnotify`), a no-op outside systemd.

## depends_on, jobs, profiles

- vops always waits for readiness between services, so `service_started` behaves like `service_healthy`: stricter than compose, never looser.
- `service_completed_successfully` makes the dependency a job: ready = exit 0, default `restart: no` (an always-restarting job would loop), 10 min timeout. A finished job isn't rerun until its definition changes (like compose `up`); a failed one is retried on the next apply.
- When a service fails, its dependents are skipped in that apply instead of deployed against a broken dependency.
- Active profiles come from `COMPOSE_PROFILES` in the project env (the compose-standard variable, set the vops way). `depends_on.restart` is rejected: vops never restarts dependents behind your back.

## Config: vops.yml and its lock

- One committed config file, `vops.yml`: domain, email, listeners, tls, snapshots, images kept (`image_keep`), preview limits. Desired state like compose files: a change shows in the plan (`~ ui: a -> b`) and takes effect on apply.
- The host keeps `~/.vops/config.yml`, a copy of the last applied `vops.yml` (the "lock"). The daemon always starts from the lock, never the repo, so a broken or half-pushed `vops.yml` can't stop it: the plan warns "keeping the config in effect" and nothing changes. `vops install` sends the local `vops.yml` as the first lock, so daemon and proxy start with the right ports and tls before the first sync. A hand edit of the lock is drift: the next plan shows it and apply restores `vops.yml`.
- Listener changes need new sockets, and only the owning process restarts, by re-exec'ing itself (same pid, systemd doesn't notice, containers keep running): http, https, tls, acme email restart the proxy (sites blink), `ui` restarts the daemon (sites don't notice). After writing the lock the daemon tells the proxy to re-read it (`POST /reload`); the proxy compares with what it runs and decides. Everything else (domain, snapshots, preview limits) applies live in both.
- Parsing is strict: a typo in `vops.yml` is an error. Every key has a default, so a new key (like `image_keep`) absent from an existing `vops.yml` or lock changes nothing on upgrade.
- HTTPS listens even before a domain exists (it arrives with the first sync); until then port 80 serves plain http.

## Snapshots and rollback

- btrfs subvolume snapshots, not copies or dumps: O(1), atomic per volume, copy-on-write, database-agnostic. Anything with a journal (postgres, mysql/innodb, sqlite) recovers from a crash-consistent snapshot like from a power cut.
- Data dirs become subvolumes when vops creates them (empty volume `_data`, missing bind dir). A non-empty plain dir is never moved: it shows as "not covered". A bind-mounted file (config, sqlite db, socket) is mounted as it is: never turned into a dir or a subvolume (a sqlite file is covered by snapshotting the dir that holds it).
- Rootless: files belong to subuids and btrfs only lets the owner snapshot or remove a subvolume, so every btrfs op runs in `podman unshare`. Deleting uses `property set ro false` + `rm -rf`, allowed to unprivileged users since linux 4.18. No root, no `user_subvol_rm_allowed`.
- Snapshots live in `~/.vops/snapshots/<project>/<time>`, on the data's filesystem (btrfs can't snapshot across filesystems). Metadata in sqlite: `snapshots` (one moment) + `snapshot_volumes` (a row per volume). Data is found from both the containers' mounts (what runs) and compose (what should run), so a disabled project can still be snapshotted.
- Pre-deploy snapshot whenever a project gets a create/update, of all its data, not just the changed service's (a migration job changes the db's data without redeploying the db). Running containers using the data are paused (milliseconds) so all volumes are captured at one instant. A failed pre-deploy snapshot aborts that project's deploy: deploying without the safety net must be a decision (`snapshots: off`). It runs before the networks are ensured (a changed network removes the project's containers), so a snapshot failure leaves everything running as it was.
- A container that can't be paused aborts the snapshot (or preview copy): those already paused are unpaused (context ignoring cancellation, failures printed) and nothing is recorded, since a snapshot of a container still writing isn't one instant. A daemon dying mid-snapshot leaves containers paused, so boot (`StartStopped`) unpauses every vops container in `paused` state.
- Restoring data stops the project's containers, snapshots the current data as `pre-rollback` (undo point), restores each volume (the live one is moved aside, put back if the restore fails) and starts what was running. If a volume fails after others were restored, those are put back from the undo point, so the project starts on its pre-rollback data, never on mixed instants. If that fails too (or there is no undo point) the project stays stopped, an `error` event is recorded and the error says how to recover (`vops rollback <p> --snapshot <id>`, then `vops restart <p>`): a database next to the uploads of another day is worse than downtime.
- Retention: newest `snapshot_keep` (5) automatic snapshots per project; manual and uploaded ones are never pruned. A data rollback prunes only after the restore: its undo point would otherwise push out the very snapshot it puts back.
- Backups are snapshots as files, not `btrfs send`: a .tar.gz (`vops-backup.json` first, then a dir per volume) opens anywhere and needs no btrfs on the other side. Export runs GNU tar inside `podman unshare` per volume (subuid owners are plain uids there, so numeric owners, modes and xattrs survive) and Go rewraps the entries into one stream: nothing buffered on either side. Import: Go reads the upload, checks each entry and pipes the good ones to `tar -x` in the namespace, one new subvolume per volume, made read-only at the end. Checked in Go before tar sees anything: manifest first; volume names are the project's data today (a subset is fine: restore puts back only those); no absolute paths or `..`; only files, dirs and links (no devices, fifos); hard links stay in their volume; nothing goes through or replaces an archive symlink (so an archive can't write outside its dir whatever tar's defaults). Any failure deletes what was extracted and records nothing. The result is a snapshot with reason `upload`, never pruned; restoring it is the usual data rollback, with its undo point. A full-data download is "snapshot now, then export it", so it is consistent too. Incremental `btrfs send` stays an idea for big data.
- Data rollback is per project, never per service: snapshots capture all of a project's volumes at one instant and restoring only some would mix instants (a db no longer matching its uploads). Proposed and rejected on purpose. Images can roll back per service (each service is one image).

## Rollback: images and data

- A rollback returns to "right before deploy #N": the images of the project's previous deploy row (what ran right before #N, the "from" side of #N's image changes) and #N's snapshot (data right before it). Same meaning as a row's `snapshot_id`, so one id says everything and every timeline node offers the same action. No previous row: images aren't available for that point.
- `vops rollback <project>` without an id goes to right before the newest deploy that isn't a rollback ("undo the last deploy"); run twice it targets the same point, so it doesn't ping-pong.
- Parts: images and data by default (whatever is available: a point without a snapshot rolls back images only, and says so); `--images`/`--data` restrict and fail if that part isn't available; `--service` restricts images (not with `--data`: data is whole-project); `--snapshot id` restores any snapshot's data, images untouched. The dashboard dialog has checkboxes, everything available checked.
- Images roll back without git, by pinning: a `pins` row (project, service, image, digest, compose's image at pin time, the deploy that ran it). The plan runs the pinned `image@digest` instead of compose's image, like a preview override, so a pinned service has no pending change and "the host differs from git" stays quiet. Rewriting git (a revert commit on the host) was rejected: the host repo would diverge from every laptop, and a registry push (the usual way to deploy an image) has no commit to revert.
- Only what changes is pinned: a service whose target equals what compose asks for now loses its pin instead. Undo falls out of the same rule, and a rollback never leaves pins that do nothing.
- Only images with a digest can be pinned: own-registry images and pulled images with a repo digest (`repo@sha256:…`). Built images and `localhost/` images without one are skipped as "can't roll back without the code (git)"; the rest still rolls back. See TODO.md for tagging built images per commit.
- Pins expire when a newer version arrives (a pin is an emergency state, not a way to run production): a registry push that would redeploy the service (a tag it runs; not with `x-vops.watch: false`, not preview tags) drops the pin and deploys; an apply where the service's compose `image:` differs from the pin's recorded one (or the service or project is gone) drops it. Env, ports and other compose changes keep the pin and redeploy with the pinned image. Dropping records an event; the plan shows it (`@ web: pin to #12 dropped (compose says … now)`).
- `vops unpin <project> [service...]` and the dashboard's Unpin remove pins and redeploy only those services (rolling). Other pending changes wait for an apply, so an unpin never deploys something nobody reviewed.
- Previews ignore pins: they follow compose and their own overrides.
- Pins show everywhere a service does (`vops status`, `vops plan`, a "pinned · #N" badge with Unpin in the Services tab and the overview's list, an overview warning): a forgotten pin would silently keep an old version in production.
- Order: images only = an apply of the pinned services (preflight pull of every target first, rolling, no downtime, the usual pre-deploy snapshot). Both = preflight images, stop the project, `pre-rollback` snapshot, restore, set pins, start the unchanged services as they were, deploy the pinned ones. A preflight failure (image gone, pull fails) changes nothing.
- The rollback row records `before_id` (right before which deploy), `parts` (`images`, `data`, `images,data`; old rows are `''` = data), `restored_id`, and the images after, as usual. Undoing rollback R = rolling back to right before R with R's parts (also when restoring R's undo snapshot with `--snapshot`); `undoes` = R. The "pin only if different" rule removes R's pins or puts earlier ones back.
- Code and compose rollback stay a git operation: the rollback dialog (and cli plan) show the data's commit next to the running one and, when they differ, the exact commands (`git restore --source=<sha> --staged --worktree -- <project>/`, commit, `vops sync`). Git stays the single source of truth; a rollback rewriting the host repo would diverge from every laptop. Images are the exception because they don't live in git: pins cover them.

## Deploy history and the timeline

- `deploys` table: one row per project per apply that changes it (any action other than none, or a plan error), and one per rollback. Written by the engine (`applyProject`, `Rollback`), so cli, dashboard and registry pushes are all covered; the caller only names the trigger (`sync`, `apply`, `ui`, `push`, `unpin`; the engine sets `rollback`). A no-op apply records nothing. Previews have no rows (the previews table is their record). The row is written when the deploy ends (no "running" state a crash could leave behind); recording never fails a deploy.
- `snapshot_id` is always the data right before that event: the pre-deploy snapshot for a deploy, the pre-rollback snapshot for a rollback. One meaning, so every node's "Restore data" and "Preview from here" start from the moment before it happened. The alternative (a deploy owns the next deploy's snapshot, "its data at the end") needs the next row to exist and makes rollbacks a special case.
- Images: what runs after the event, per service, read back from podman: a service whose containers carry the desired hash runs the desired image (the hash covers our registry's digest; a pinned service records the pinned image with its original tag); otherwise (a failed update kept the old replicas) the previous row's entry is carried over. Digests: our registry's from the plan, pulled images' from `podman image inspect`, none for `localhost/` and built images (marked `built`: the commit rebuilds them).
- Own-registry images referenced by digest (`registry.<domain>/shop/web@sha256:…`, how a preview pins a past deploy's image) run the loopback pull ref directly, since a digest can't be a local tag. So "Preview from here" gets exactly the bytes that ran, even after the tag moved.
- The project banner "Rolled back to before #N (images, data) · Undo" shows while the project's newest row is a successful rollback that isn't an undo; the next deploy (or the undo) clears it. It comes from `last_deploy` in `/api/status`, so it shows on every tab with no extra polling.
- Retention: 5000 rows host-wide (a trigger, like events). The timeline shows a project's newest 100 deploys; snapshots referenced by rows show on them, others (manual, older pre-deploy/pre-rollback) are their own nodes. Pruned snapshots vanish from their row ("no snapshot").
- Previews record `deploy_id`: the node they branched from (the node picked in the dashboard; for live data, the project's newest row at creation; 0 from a snapshot, which places them on the node showing it), shown as chips on the timeline.
- The Data tab was folded into the timeline: coverage warnings on top, "Snapshot now" on the "now" node, delete on snapshot nodes. One place for "what happened to my data".
- `/api/timeline?project=` returns everything the tab and `vops history` need in one call (rows, snapshots, image changes vs the previous row, preview chips, images gone from the registry, commit subjects via one `git log --no-walk`), so both render the same. `GET /api/rollback` is the rollback plan (dialog and cli confirmation print the same); `POST` runs it.

## SQL: sqlc, migrations, triggers

- sqlc (same config as golang-tmpl): SQL in `internal/store/queries.sql`, schema in `internal/store/migrations/*.sql`, generated Go committed in `internal/store/queries/`. The store package keeps only what SQL can't do (encryption, hashing, json repos) and friendlier types. sqlc is a dev tool only: `go install` and the binary don't need it.
- Migrations run in name order, each once, in a transaction, tracked in `schema_migrations` (the golang-tmpl runner).
- The audit log is written by triggers on every table, so no code path can forget it. Triggers never copy secrets: env values, users' secrets (only "new password"/"new token") and session ids are left out (sessions show 8 chars of the id hash and their user). Retention is a trigger too (20k audit rows, 5k events).
- `events` (human-readable, written by code) and `audit_log` (every db write, by triggers) are separate on purpose: one says "deployed shop/api", the other "projects.commit changed".

## Small ones

- Nothing deploys without an explicit apply: env changes, enable/disable and plain `git push` only show as "pending" (cli `status`, dashboard banner). The exception is the registry push trigger, which is its point.
- cli `apply` shows the plan, then applies the exact commit it showed (`--commit`), so a push in between can't sneak in. A plan error in one project (bad compose, image not pushed yet) fails that project only; the others still apply.
- Env values, admin passwords and chosen tokens travel over ssh stdin, never as command-line args (no `ps`/history leaks).
- The unix socket lives in `~/.vops/`, so the home path must be under ~100 chars (unix socket limit). Real homes are.
- Wrong credentials are limited per client (ip, or ipv6 /64), dashboard and registry together: 10, then `429` until 15 minutes pass without a new failure, with one `auth` event. An attempt is reserved before the check so parallel guesses can't skip it; a success gives its attempt back but forgives nothing (a valid deployer token buys no admin guesses). At most 4 password checks (pbkdf2 600k) run at once so a flood can't take every cpu, and a failed login still costs 1s. No global lock: it let an attacker queue in front of the real admins. Unknown users run a dummy pbkdf2, so timing doesn't reveal who exists. The internal pull user is never limited.
- api json tolerates invalid utf-8 and truncations cut on rune boundaries: container output cut mid-rune used to make `encoding/json/v2` fail and send an empty 200.
- The web api validates what it takes (project paths, service names, env keys, user names) before the db, podman or the disk see it. Tracked files are read through `os.Root`: a symlink can't lead out of the repo.
- `secret.key` of the wrong size is an error and the file is left alone; only a missing key is generated (replacing it would make every env value unreadable).
- Every `podman.Run` has a timeout (2m + the `-t` grace period; 30m for pull/build): a hung podman (storage lock, dead mount) would otherwise hold the deploy lock forever and block every apply and restart. Log streams are exempt.
- A daemon crash doesn't touch containers (`KillMode=process`, systemd restarts it in 2s, routes rebuilt from labels) nor sites (the proxy is another process). Only the dashboard and registry are down for those seconds: the proxy answers 502 with a clear text for their hosts.
- Removing a container counts as done when it is gone, even if podman errors cleaning up its network afterwards (seen with nested podman).
- The daemon idles at ~16MB RSS.
- Tests: `just test` runs with `-race`; they share one isolated podman storage (`~/.cache/vops-test`) behind a file lock, so `go test ./...` runs packages in parallel safely. Fuzz tests (`FuzzSplitPath`, `FuzzLoad`) run their seed corpus in every `go test`; `go test -fuzz` explores (the registry path splitter and compose loader are what network and git feed). `just vps-test` is the production-like check: fake ssh in `go test` covers the logic fast, the vps container covers real sshd/systemd/root.

## The proxy process

- `vops proxy` owns :80/:443 from the config lock, autocert (same `~/.vops/certs` and host policy: `vops.<domain>`, `registry.<domain>`, routed hosts), http→https redirects, HSTS and the routing table. It imports `config` and stdlib only (no sqlite, podman, registry or deploy engine), so there is little to crash.
- The daemon has no public listener. It keeps `vops.sock` (cli) and `ui` (loopback by default: `vops ui` tunnels, and podman pulls from our registry; with `ui: off` a random loopback port serving only the registry keeps pulls working, rather than refusing `ui: off`, which would break hosts whose lock already has it), and serves `vops.<domain>` and `registry.<domain>` on `web.sock` (0600), where the proxy forwards them with a plain `httputil.ReverseProxy`: bodies stream both ways (registry pushes, log follows), no size limits, no read/write timeouts (only 10s for headers). The daemon trusts the forwarded client ip and scheme there (login events, `Secure` cookies). Daemon down → those two hosts answer 502 "the daemon is not running", every site keeps working.
- Protocol, on `proxy.sock` (0600, http): `PUT /routes` swaps the whole table and answers after the swap, `GET /status` (proxy.Version, vops build, route count, table hash, pid, last push, 429/413 counts per project), `GET /routes`, `POST /reload` (re-read the lock), `GET /ping`.
- The daemon stays the source of truth (routes rebuilt from podman labels). Every change of its table (`proxy.Table.OnChange`) sends the whole table, synchronously: a rolling release's switch returns after the proxy swapped its map, so drain-then-stop stays correct. Whole table, not diffs: tables are small and a push can't be half-applied or out of order (pushes are serialized and always send the current table). The housekeeping tick (every minute) rebuilds from podman and resends, so drift heals itself.
- Proxy unreachable during a deploy: the deploy goes on (the proxy serves its last table), the daemon logs it, records an event, and resends every second until the proxy answers (recording that too). Except the switch of a rolling release: draining old replicas unconfirmed could leave the proxy routing to removed containers. `Table.Set` returns the push's error; the rolling path retries up to 10s, then puts the old routes back, removes the new replicas and fails ("proxy did not confirm the new routes; old replicas kept serving"). A recreate, a removal or a route refresh never fails on the proxy: there is nothing to keep serving.
- The proxy writes `routes.json` (write, fsync, rename; any error keeps the old file) after each push that changes it and loads it at start, so it comes back with the right routes after its own restart even with the daemon dead. One writer, the proxy: the file is exactly what it last served. With the daemon writing it, file and proxy memory would be two copies with two writers, and a proxy that missed pushes while down would still need the daemon's retry.
- `proxy.Version` (an int) is the proxy's behaviour plus this protocol. Bump it when either changes, and only then: it makes `vops setup` restart the proxy. A daemon change never needs it.
- Limits (`x-vops` `rate`, `burst`, `max_body`, `timeout`, top level of compose) are per project, in the routing table (`limits` on each route; `omitempty`, so tables without limits hash the same). They live in git like everything else (a dashboard-only toggle would be drift); an emergency override table is still an idea (TODO.md). Apply records them in `projects.limits` and the table is built from podman labels plus that column, so a change is its own plan line and never recreates containers (labels would have, or gone stale). Previews use their project's. The proxy keeps a token bucket per (project, client ip) in memory, purged after 10 idle minutes; the client ip is the tcp peer (the proxy is the edge; `X-Forwarded-For` is the client's own text). `max_body` refuses on `Content-Length` and cuts chunked bodies with `http.MaxBytesReader` (the ReverseProxy error becomes `413`). Sizes are 1024-based (`10MB` = 10485760 bytes), matching podman and upload-limit intuition. 429s and 413s are counted per project in `GET /status`. The dashboard and registry hosts are forwarded before routing, so never limited.
- Upstream timeout: 60s for a container's response headers; `x-vops.timeout` (top level, whole seconds, in the limits) sets it per project for long polling. It is per request (a timer started once the request is written, via `httptrace.WroteRequest`, cancelling the round trip until headers arrive, so a slow upload is never a 504), not the Transport's `ResponseHeaderTimeout`, because the Transport is shared by every project. The body is never timed, so SSE and downloads stream as long as they want. Past it: `504`. An upgrade (`101`, websockets) keeps its writable body, so it passes through untimed.
- Edge hardening, all in the proxy, none configurable (defaults no real client reaches): `ReadHeaderTimeout` 10s, `MaxHeaderBytes` 64KB, a request body with no byte for 30s is dropped (`408`; a read deadline reset before each read and cleared at EOF, not a total `ReadTimeout`, which would kill big uploads that keep moving, nor cut a response still streaming after the body), at most 256 connections per client ip and 10000 total (a wrapping listener closes extras at accept, http and https counted together).
- `X-Forwarded-For` (and `-Host`, `-Proto`) are overwritten, never appended to: `ReverseProxy` with `Rewrite` drops the client's before `SetXForwarded`. So what the daemon trusts on `web.sock` (and apps behind the proxy) is the tcp peer, not client-written text.
- Visibility: `/api/status` has `proxy` (up, version, routes, in sync = table hashes match) and adds a warning when it is down, out of sync or on another version. `vops status` prints it on the first line; the dashboard shows it in the top bar and the overview warnings.

## Versions: cli vs host

- The cli sends its version with every forwarded command (`VOPS_CLIENT=v1.3.0 ~/.vops/bin/vops --local ...`: an env assignment, so hosts from before the check ignore it). The host refuses when major.minor differ, exit code 3: older cli → "update yours (go install ...)", newer cli → "run `vops install` to upgrade it". Patch differences are fine; `version` always answers; `setup` is exempt (install already decided). Dev builds (no parseable version) skip it with a one-line warning. Versions come from `-ldflags -X main.version` or the module/VCS version Go stamps (`v1.2.1-0.2026…+dirty` counts as 1.2).
- No extra ssh round trip for this. A newer cli against a host from before the check can't be caught by the host; `sync`/`apply` catch it anyway: their plan carries the host's version since 1.3, so a plan without one is a 1.2-or-older host.
- `vops install` reads the host's version in its probe and prints "installing", "upgrading vX → vY" or "reinstalling vX". Installing an older major.minor over a newer host is refused unless `--force` (a teammate with an old cli would otherwise downgrade production). With `--binary`, the version is asked from that binary (or read from its build info when it's for another arch).

## Previews

- A preview is the synthetic project `<project>@<name>`, run by the same engine (labels, hashes, plan/apply, rolling releases). `@` can't be in a dir name, so it never clashes with a real project. Podman objects use the slug `shop--pr-42` (a dir could produce that slug, so `preview up` refuses a name whose slug or dns name belongs to an existing project); domain `<service>.pr-42.shop.<domain>`, which autocert already handles.
- Previews are not in the plan: git doesn't describe them. `Plan` ignores containers of `@` projects (else they'd be "removed from git"); the `previews` table is their desired state (commit, image overrides). No pre-deploy snapshots of them, no `projects` row.
- Code: a detached git worktree of the host repo in `~/.vops/previews/<slug>`, at the project's applied commit (or `--ref`). It gives each preview its own bind paths, build contexts, `env_file`s and `preview.env` at that commit without copying. The commit is pinned: later pushes and syncs don't move it, `preview up --ref` does. `vops preview up --ref <branch>` pushes a local branch to the host first (never `main`), so `--ref` works from the laptop.
- Data: only the volumes and binds (inside the project dir) of `x-vops.preview.copy` services, copied once at creation as writable btrfs snapshots straight from the live subvolumes (the project's containers paused for the milliseconds it takes, like a pre-deploy snapshot). No snapshot row is recorded, so previews never push pre-deploy snapshots out of retention. `--from <id>` copies a recorded snapshot instead. Updates keep the preview's data; to start over: `rm` + `up`. Volumes map by compose key (`vops-shop-db` → `vops-shop--pr-42-db`), binds by path inside the project dir (into the worktree). Everything else starts empty; a volume a copied service shares with another running one is copied (the plan warns). A service added later (a push of another declared service) starts empty: the copy is made once. Without btrfs a preview starts empty.
- Env: two layers only, never production's: `preview.env` in the project dir (committed, not secret: `SMTP_HOST=mailpit`), then preview secrets (`vops env set shop --preview KEY`) on top. Copied data still carries production's credentials (db passwords): set what the preview needs with `--preview`. Preview secrets live in the `env` table under project `<project>@*`: same encryption, write-only api and audit, no new table. `COMPOSE_PROFILES` comes from these layers; `VOPS_PREVIEW` is set.
- Guardrails are defaults, not options: no shared `vops` network (a service asking for it gets the preview's default network), only declared services run (below), no published host ports (they'd clash with production), no `x-vops.domains` (production's), `name:` of volumes and networks ignored (it would be production's object), external volumes used by running services are an error. External networks and absolute bind mounts are kept (the plan warns about the latter): explicit infrastructure.
- Limits: `preview_max` (5) previews on the host, counted from the table; `preview_ttl` (3d) since the last `up` or push. Housekeeping checks every minute. Both live in `vops.yml`.
- Opt-in per service (`x-vops.preview: {with, copy}`), not per project with opt-outs (the old `x-vops.previews` pattern + `preview.skip`). A preview carries production data, so what runs and which data is copied must be written down: a new worker, cron or database doesn't silently start in every preview on a copy of production. `copy` is separate from `with` because copying is the risky part (personal data, queued jobs); `copy` implies `with` (copied data nobody runs is useless). A preview runs the services it is for plus their `with` and `copy`. "The services it is for" is stored (`previews.services`): the services pushed or given with `--image`, accumulating like image overrides; empty = every declared service (a plain `preview up`, "New preview", "Preview from here"), and such a preview stays that way when pushed to, so it never shrinks. Images of a timeline node are pins, not what the preview is for; overrides of services that don't run are ignored for them, an error for `--image`. A required `depends_on` outside a declaration's set is a compose error (it used to be dropped silently, giving previews that start and fail at runtime). Not transitive: a `with` service's own declaration pulls nothing more in; name it.
- Registry trigger: a fixed tag prefix `preview-` (one rule to learn, no per-project pattern; the tag-deletion idea can match it). A pushed `preview-<name>` creates or updates preview `<name>` in every project where a service running that repo has `x-vops.preview`; services running it without one are skipped with an event. The image keeps its registry host and gets the pushed tag. Overrides accumulate: `shop/web:preview-pr-42` then `shop/api:preview-pr-42` is one preview with both declarations. A `preview-*` tag is never a production redeploy, even if production runs that exact tag.
- `rm` removes containers (and anonymous volumes), networks, volumes, built images and local tags of the overrides, then the worktree with its data, then the row. If a step fails the row stays, so a retry or the ttl finishes the job. Registry tags stay (the user's pushes).
- Removing a container also removes its anonymous volumes (`podman rm -v`), for previews and projects alike: an image's `VOLUME` (postgres has one) left a volume behind per removed job or replica, forever.
- Preview lifecycle events are recorded under the base project (kind `preview`), so `vops events shop` shows them; deploy lines use the preview path.
- Dashboard: Previews tab per project, previews as subtle rows under their project in the sidebar, a count on the overview. The "copy of production data" warning shows once, atop the tab, not per preview. The empty state explains the `preview-*` push with a command built from the project's declared images; with no declaration it shows the `x-vops.preview` snippet to add, built from the project's services (`preview` on each service in `/api/status`). Preview logs are `/api/logs?project=shop@pr-42` (same labels and journald tags as projects) on the full-page log view. The Environment tab switches between production and preview secrets (`?scope=previews`), with a line saying previews don't inherit production's env and read `preview.env` from the repo.

## Secrets backup (.secrets.age)

- Git rebuilds everything but env secrets, which live only in `~/.vops/vops.db`, sealed with `secret.key` on the same disk. So the repo gets `.secrets.age`: age, armored, a sorted commented .env per project and scope (`[shop]`, `[shop previews]`, Go-quoted values so newlines survive). age because it encrypts to ssh public keys (`agessh`): whoever can deploy can decrypt with the key they already have, and nobody learns a new concept. Users never run age; `age -d -i ~/.ssh/id_ed25519 .secrets.age` is an escape hatch.
- It sits at the root (not in a project dir, so never part of a project's files or plan). Repos ignoring dotfiles (`**/.*`) would drop it, so the cli checks `git check-ignore`, adds it with `-f` and prints the `!/.secrets.age` line to add.
- Recipients are computed on the host, not configured: the vops user's `authorized_keys` (read live: whoever can deploy), root's (hosting panels inject their key there; the daemon is rootless, so `vops setup` copies it with `sudo -n`: never a password prompt, never writing under `~/.ssh` or `/root`; without sudo the last copy stays), and `secrets.recipients` in `vops.yml` (desired state: a plan line, effective on apply). Only ed25519 and rsa work with age: others (ecdsa, `sk-*`, `cert-authority` lines) are listed as skipped with the reason. Options (`command=`, `from=`) are parsed by `ssh.ParseAuthorizedKey`. Duplicates count once.
- The host encrypts (it has the plaintext and only needs public keys) and keeps the latest blob in `~/.vops/secrets.age`. age output is random, so it re-encrypts only when an HMAC (key derived from `secret.key`, never a plain hash of secrets) of plaintext + recipient keys differs from the one in `meta`. Checked after every env write (cli, dashboard, preview secrets, rm, restore), on vops.yml apply, at start, every minute (authorized_keys edits) and on request.
- No usable recipient: no new backup; the previous one stays and the warning shows in `vops status`, the dashboard and every sync. No secrets ever: no file.
- The host never commits (its repo is the push target; commits there would diverge from every laptop). The cli commits only that path (`git commit --only`, so the user's staged work stays staged): `vops env set/rm` right away, `vops sync` after its pull and before its push, so a dashboard change reaches git on the next sync; status says "behind" meanwhile. A merge whose only conflict is `.secrets.age` (two laptops committed different versions) takes either side: sync writes the host's latest right after.
- A copy in git this host didn't write is never replaced while it holds secrets the host lacks. The host lists the sha256 of every blob it wrote (`secrets.known`), telling "older version of ours" (replace) from "another host's" (new or reinstalled host: restore first) without decrypting. Otherwise a fresh host's first sync, or an `env set` before it, would overwrite the only backup with an almost empty one. Sync offers the restore (`[Y/n]`, `-y` = yes, no terminal and no `-y` = a warning); declined or undecryptable, the file stays and sync goes on. `vops env restore [file]` does it explicitly. `git rm .secrets.age` starts over.
- Restore decrypts on the laptop (private keys never go to the host): the `--ssh-key`/lock key, then `~/.ssh/id_ed25519`, `id_rsa`, other `id_*`; encrypted keys ask their passphrase (no echo) only when the backup is encrypted to them. ssh-agent can't do age's key exchange, so a key only in the agent is reported as such. Values travel as plaintext over ssh stdin (never argv, never a file) to a socket-only route that sets missing keys with `INSERT … ON CONFLICT DO NOTHING`: existing values always win. Each restored key is an event.
- History is the limit: a removed key still opens old commits. Documented (rotate secrets when removing someone) rather than worked around; rewriting history is not ours to do.

## Notifications

- Web Push, implemented with the stdlib (VAPID: an ES256 JWT, RFC 8292; payloads aes128gcm, RFC 8291, `crypto/ecdh` + `crypto/hkdf` + AES-GCM), tested against the RFC's test vector. No ntfy/Pushover/Firebase account: the browser vendors' push services are the only third party and see only ciphertext. Outbound webhooks are the next step (TODO.md).
- Nothing in `vops.yml`, on purpose: who gets what on which device is per person, not server desired state, and thresholds are tuning, not config worth a plan line and review. Everything lives in the db (`push_subscriptions`, `alerts`, `notify_prefs`, `notify_settings`) with audit triggers, edited from the dashboard. Defaults are chosen so nobody needs to touch them.
- The VAPID keypair is generated once and kept in `meta` (`vapid_private`). It is not in the secrets backup: losing it (new host) only means every device resubscribes with one click, while backing it up would put another private key in git history. JWT `sub`: `mailto:<email>` from `vops.yml` (the ACME email), else `https://vops.<domain>`, else `mailto:vops@localhost` (push services want a contact; none requires it reachable).
- iOS only delivers Web Push to web apps added to the home screen, so the dashboard has a manifest (`display: standalone`, PNG icons) and says so on iOS. The service worker (`/sw.js`, root scope, no caching) only shows notifications and, on click, focuses a dashboard window and sends it to the alert's page (`postMessage`; `navigate()` only works on controlled clients). `localhost` is a secure context, so `vops ui` works too.
- An alert is a row with a key (`restart:shop/web`, `down:shop/web`, `resources:disk:/home`, `oom:host`) and at most one live (`ended_at = 0`) per key, a unique partial index. States: open (being sent), silenced (by someone, for everyone), expired, resolved. Silenced and expired stay live until their condition ends, so they don't reopen next minute. Every new alert is also an `events` row (kind `alert`). Retention: 2000 rows (a trigger, like events).
- Repeat and expire (1h, 24h): a down site nobody acts on keeps reminding, but not forever (one push an hour for a day, then nothing). Event kinds (deploy failed, restart, oom) coalesce on their key: a crash loop is one alert with a count in its title, re-sent on the repeat schedule, not per crash; it ends after 30 quiet minutes. Condition kinds (down, health, resources) end when the detector stops seeing them for 3 cycles. The state machine is one pure file (`notify/alert.go`, time injected), unit tested.
- Resolved notifications exist but are off by default (they double the pushes for little; the dashboard shows the state anyway). Successful deploys likewise (off); a successful deploy ends the project's `deploy_failed` alert.
- Container deaths come from `podman events --filter event=died` (instant; reconnects with backoff), each judged 3s later: vops' own stops are not alerts. The engine marks every container it stops, removes or restarts (apply, rolling releases, rollback, restart, previews, network recreation; the mark lives 10 minutes and one death consumes it); a container gone by then was removed (only vops removes them); jobs are meant to exit; previews aren't watched; nothing is judged once the daemon is stopping (a host shutdown kills everything). The stream can miss deaths (reconnecting, podman restarted), so housekeeping reconciles every minute: restart counts and finish times against the previous pass, minus what the stream saw; a pass during which the engine moved containers only re-baselines. Lock-based suppression alone ("ignore events while deploying") was rejected: the engine lock is global, so it would hide real crashes of other projects during long deploys.
- `podman kill` (SIGKILL, exit 137) raises a restart and an oom alert: from outside, a SIGKILL looks the same whether a person, the kernel OOM killer, systemd-oomd or earlyoom sent it.
- Down and health: a probe every 30s per routed service of enabled, non-preview projects (`x-vops.health` if set, else a TCP connect to its 127.0.0.1 port; compose healthchecks via `podman healthcheck run`, as readiness does), `down_after` (3) failures in a row. A round overlapping an engine operation (a generation counter bumped when one starts and ends) is thrown away and keeps live alerts alive: a deploy is not an outage.
- Resources: sysmon samples every 30s in the background (the System page shares the samples). Containers are read straight from cgroup v2 files (`memory.current/max/events`, `cpu.stat/max`, path from `podman inspect`, works rootless), not `podman stats` every tick. Host oom kills come from `/proc/vmstat` `oom_kill`, containers' from `memory.events`.
- Early killers: on rootless hosts systemd-oomd watches `user@.service`, which holds the daemon, proxy and every container, and may pick the proxy; earlyoom picks the biggest process. Unprivileged units can't lower their `OOMScoreAdjust`. So vops warns before they act (PSI `some avg60` > 20%, memory available < 10%) instead of changing containers' `oom_score_adj`: that flag is part of the service hash, so setting it would redeploy every service on upgrade.
- Access: one function, `notify.CanSee(user, project)`: global users see everything; others the projects whose services run one of their repos; host-wide alerts only global users. Today only admins (global) log in, so it is future-proofing for roles, used by the sender, the alerts list and the badge.
- Anyone logged in can silence any alert and remove anyone's device: the people who can log in are the same small team, and a stale device (a lost phone) must be removable by whoever notices.
- Sends run in background goroutines with a 10s timeout per push service, `TTL` = the repeat interval (capped at 24h), `Urgency: high` for down and oom. A 404/410 deletes the subscription (an event says so); other errors show on the device row.
